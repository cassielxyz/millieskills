# Memory & Orchestration Interop

Millie must work alone. External memory/orchestration systems are optional accelerators.

## brain.md
If root `BRAIN.md` and its CLI contract are present:
- read relevant durable decisions before major design work;
- write only durable decisions/requirements/constraints through the brain CLI as its protocol
  requires;
- do not hand-edit brain files if the project's BRAIN.md forbids it;
- do not duplicate raw token values/components that are obvious from code/DESIGN.md;
- suitable memory: "transaction surfaces must remain motion level <=2 because compliance reviews
  require predictable focus/order";
- unsuitable memory: "button radius is 8px" when token source already says so.

## Superpowers
If Superpowers is present, its planning/testing/review process may wrap large implementation work.
Millie owns UI/UX/creative design domain decisions. Do not let mandatory brainstorming workflows from
another skill block a tiny local visual fix unless that runtime explicitly requires it.

When evolving Millie itself, borrow the useful TDD-for-skills principle: pressure cases before/after
skill changes and close loopholes.

## Ruflo / subagents
For large work, optional specialist stages:

```text
researcher -> UX -> visual direction -> frontend -> motion/3D -> accessibility/perf reviewer
```

Parallelize independent research/verification, not tightly coupled visual decisions that need one
coherent art direction.

## Freebuff / other multi-agent runtimes
Treat as execution environments. Millie's folder/relative-reference design must remain portable and
must not assume one orchestration API.
